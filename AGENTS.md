# AGENTS.md — urx-cli

## Overview

The `urx` command line tool for the YAMAHA URX22 / URX44 / URX44V: one-shot reads and writes, watches, command files, an interactive console and settings-file import. It consumes the shared library [urx-device](https://github.com/semnil/urx-device) as a pinned Git submodule at `vendor/urx-device`: device definitions, semantic operations and the Device Center transport live there, not here.

## Structure

- `src/` — the command: argument grammar, help and version, terminal and JSON output, exit codes, process lifecycle. `src/cli/commands.ts` is the command-binding table that the parser and help both read. `src/result.ts` holds the result record, the E2 cause identifiers and the exit code each takes; `src/messages.ts` their English explanations; `src/diagnostics.ts` the standard-error diagnostics; `src/device-list.ts` runs `urx device list`. `src/main.ts` loads a device command's module, and the addon with it, only when that command runs
- `native/` — the Node-API addon (napi-rs) over the urx-device transport crate. `src/native/addon.ts` loads it and checks its build identity before any device access; `src/native/device.ts` discovers, selects, opens and closes devices through it, validating every record with urx-device's validators; `src/native/transport.ts` is urx-device's `Transport` over one addon connection, returning each native request record as it came for urx-device's operations to validate and throwing subscription failures as urx-device's `OperationFailureError`; `src/native/notifications.ts` validates each notification batch the addon delivers, hands its records to the subscriptions they name and acknowledges it, and closes the connection instead when it cannot
- `launcher/` — the installed `urx` command (Rust): it takes the installation's shared use protection on `gate.lock`, checks that the state record beside it names this bundle's release manifest as complete, removes inherited `NODE_` variables and hands the arguments, unchanged, to the bundled Node running `app/main.js` (`execve` on macOS, a waited-for child on Windows). It parses no command; a failure before Node starts exits 1 with one line on standard error. `launcher/examples/fake-runtime.rs` stands in for Node in its tests
- `tools/output/` — `urx-output` (Rust), the build tooling that publishes a build's output. `publish` stops when anything is at the output; otherwise it makes a work folder beside the output under a random name, writes the staged files into it through open folders (relative to open folders on macOS, under folders held without delete sharing on Windows), walks it once checking each folder is the one it made and reading every file back against the staged one, writes the record under a temporary name and renames it into place, and renames the work folder to the output only where nothing is (`renameatx_np` with `RENAME_EXCL` on macOS, a non-replacing rename of the held folder on Windows). That rename is when the build succeeds and the next stage can see the output, and nothing of the output is touched afterwards; on a failure the output's path is untouched and the work folder is left, without the record, for the user to remove. An output that appears at the path while a build runs is named as another build's or program's, not as one to remove. The release, bundle and installer builds build it from the working tree and call it; nothing of it is in an output
- `installer/windows/urx-cli.iss` — the per-user Windows installer (Inno Setup). It installs `dist-bundle/` under `%LOCALAPPDATA%\Programs\urx-cli` and refuses any other folder (`/DIR`, `/LOADINF`), holding the installation's gate exclusively from before its first change until it ends. The state record says `installing` before any change, notes that the `bin` folder is going onto the user's PATH before putting it there, and says `complete` only after every installed file matches the release manifest and the folder is on the PATH; a record not in exactly the form it writes, and a folder at the installation root without its record, empty or not, are left alone and stop it, as does anything Windows cannot tell it about (a file, the record or the user's PATH). It closes nothing that is running: while urx runs, it stops. Its uninstaller says `removing` only when the removal starts, after the user confirms, and deletes the state record only when every installed file and the PATH entry it added are gone; otherwise the record stays `removing` and setup or the uninstaller can run again. Without a state record the uninstaller changes nothing, since it cannot tell which PATH entry is the installer's. It keeps the gate and anything else in the folder. `scripts/build-windows-installer.mjs` compiles it, only with the Inno Setup version `build-inputs.json` records, from a checked copy of a Windows x64 `dist-bundle/` into `dist-installer/`, which it publishes as the other builds publish theirs, and `scripts/check-windows-installer.mjs` installs, refuses another folder, reinstalls, refuses to remove it without its state record, and removes it on a disposable machine
- `maintenance/` — the macOS installer and removal tool (Rust, K20, K41 as revised): `urx-install`, run from beside the release tree `urx-cli/` it installs, and `urx-uninstall`, installed as `maintenance/urx-uninstall`. Each is one process that makes every change itself, under the installation's gate held exclusively, and without `--apply` only reports what it would do under a shared hold that a running urx does not block; `--apply` needs sudo. `urx-install` takes the tree only when its release manifest has the SHA-256 compiled into it (`URX_RELEASE_MANIFEST_SHA256`; without one it installs nothing) and the tree holds exactly the files the manifest lists, each as listed and with its bundle mode; owned paths are printable ASCII, each folder spelled one way. Before the record changes it stops when the root is neither recorded tree, by device and inode, or holds anything but that tree's recorded files (a file or folder someone put there is a conflict and is kept), when someone other than root could change the folder the root or the maintenance folder is in, or one above it, or when another user could not reach the installation. Every name it makes, swaps or removes beside the root is acted on through the one descriptor of the root's parent it opened, and the work folder and the previous root are each confirmed by device and inode before the swap and before their removal. It records `installing` with every path the installation may own, and the paths and the device and inode of the tree at the root it starts from. It removes what an interrupted run left in the work folder the record names, while that folder is still the recorded object: the previous tree by its recorded paths, a partly assembled release only as far as each file holds exactly what the release lists, keeping and reporting anything else. It makes a work folder beside the root under the first name nothing is at (`urx-cli.install-<tag>`, the tag being the start of the release manifest's digest, then `-2`, `-3` and on; a folder at a name the record does not name is left as it is), 0700 while it is assembled, records its device and inode, assembles the whole release in it, verifies it, and puts it in place with one rename: a swap with the previous tree (`RENAME_SWAP`), or a rename where no root is (`RENAME_EXCL`). Nothing is recorded after the swap: which tree is at the root and which at the work folder's name is read from the objects' device and inode against the record. It then removes the previous tree, left at the work folder's name, by its recorded paths, links `/usr/local/bin/urx`, gives the gate's folder 0755 and the gate 0644 once it holds the gate exclusively, verifies the root holds exactly the release with its folders' modes (a root that does not, after an interrupted run, is assembled and swapped in again), and records `complete` last, in the form the launcher starts from. An interruption leaves at the root the previous tree or the whole release, never part of one, and only the same release finishes it. Run as root, whether other users reach the command and the gate is asked of the system by a child process switched to the user nobody; run as anyone else (a preview without sudo, the tests), it is not judged, and the preview says so. `urx-uninstall` records `removing` with the files of the tree at the root and the work folder beside it, each told by its device and inode against the record (a root that is neither recorded tree stops it), removes the link only while it points to the installation and each of those files only while it is a regular file under exactly its spelling, removes the installed `urx-uninstall` after the others and the release manifest last, removes the work folder the record names while it is that object (the previous tree by its recorded paths, a release being assembled only as far as each file holds exactly what that folder's release manifest lists, when that manifest is the recorded one; another manifest there stops it), stops with `removing` kept at a folder of the installation's, at the root or in the work folder, that is not as it made it, keeps everything else, and deletes the record once every file is gone, keeping the gate and its folder; a failure, a failed read included, keeps `removing`, and stopped once its own copy is gone it names the copy on the disk image or in the recovery ZIP to finish with. Ctrl+C stops either tool after the current operation, leaving the record for the same command to finish. Its tests run both in folders of their own, with the test's user in root's place and the test's folder as the top whose permissions are checked. `scripts/build-macos-installer.mjs` builds `urx-install` from the commit HEAD names for a checked copy of a macOS arm64 `dist-bundle/` of that commit, into `dist-installer/` (`urx-install` beside `urx-cli/`), and `scripts/check-macos-installer.mjs` installs, refuses behind a folder others cannot pass (asking as nobody) and while urx runs, repairs and removes it on a disposable Mac
- `test/device-center-peer.ts` — a controlled local Device Center peer for the addon's integration tests (K30). It answers requests and registrations and pushes the notifications a test asks for; it supplies protocol replies and faults, not a model of a unit
- `vendor/urx-device/` — the shared library at the adopted commit. Never edited here. Its control package is a pnpm workspace member (`@urx/device-control`), compiled by `pnpm build:common`; its transport crate is a path dependency kept out of the Cargo workspace, so its own checks stay in urx-device
- `scripts/` — repository tooling: `build-inputs.mjs` (checks the build inputs), `build-info.mjs` (writes `dist/build-info.js`, the versions and commits that `urx --version` shows), `build-native.mjs` (builds `dist/native/urx-native.node` with the same urx-device identity), `source-info.mjs` (how both read a checkout's versions and commits), `release-source.mjs` (the release source check), `release-build.mjs` (the release build), `build-bundle.mjs` and `check-bundle.mjs` (assemble and check the installed bundle), `compiled-modules.mjs` (the modules a release's commits compile to, which the output checks require), `inno-setup.mjs` (installs the recorded Inno Setup from its checked installer), `build-windows-installer.mjs` and `check-windows-installer.mjs` (build the Windows installer and check it on a disposable machine), `build-macos-installer.mjs` and `check-macos-installer.mjs` (build the macOS installer tree and check it on a disposable Mac), `version.mjs` (the addon crate's copy of the CLI version) and `workflow-block.test-util.mjs` (takes a workflow step's `run:` block out of the YAML, so `dependabot-auto-merge.test.mjs` runs the block itself)
- `build-inputs.json` — the exact Node, pnpm, Rust and Inno Setup versions and the Node archive and Inno Setup installer hashes a build uses, the one record of them
- `.github/required-checks.json` — the status checks the `main` ruleset requires, the only copy outside GitHub's settings

## Development

```sh
git submodule update --init
pnpm install --frozen-lockfile
pnpm build-inputs:check   # build-inputs.json agrees with .node-version, package.json and rust-toolchain.toml, and names the published Inno Setup installer
pnpm version:check        # the addon crate's version and Cargo.lock entry match package.json
pnpm typecheck            # the control package, then the source and test configs
pnpm build                # tsc emit of src/ into dist/, then dist/build-info.js from the checkout
pnpm build:native         # the addon into dist/native/; pnpm test loads it
pnpm test                 # vitest: src/**/*.test.ts, test/**/*.test.ts and scripts/**/*.test.mjs
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

A local verification names every one of these commands; a command left out is named as left out in the report.

## Boundaries

- **Device semantics belong to urx-device.** This repository owns command parsing, help, terminal and JSON output, exit codes and process lifecycle. A setting, value rule, composition order or request sequence is never re-implemented here, and there is no CLI-only setter. A missing or wrong operation is fixed in urx-device first and adopted here in its own pull request
- **Adoption is a pull request of its own.** It moves the `vendor/urx-device` gitlink to a released urx-device commit, with the adapter and lockfile changes it needs and this repository's checks. Nothing else pins the common commit, and no scheduled update moves it
- **No added device reads or writes.** A command performs the reads and writes its operations define: no equality checks, readback, status polling, retries, automatic reconnection, command replay or settings restoration. Tests compare request traces with the defined reads and writes

## Documentation

- **English is the base language.** This file is English only and has no Japanese counterpart. Every other document for readers has its English text at its own path and a Japanese counterpart beside it (`README.ja.md`, `CONTRIBUTING.ja.md`, `SECURITY.ja.md`, `CODE_OF_CONDUCT.ja.md`), kept section for section and cross-linked at the top
- **Documentation writes no control-protocol parameter number and no raw value.** It names an item the way the unit's screen, its user guide or the command's own help names it
- **This repository is public.** Raw device evidence, real device identifiers, private research notes and links to private material stay out of it — source, comments, documentation, commit messages and pull request bodies alike

## Versioning

- The root `package.json` `version` is the CLI's version and its only hand-edited copy; it is independent of the urx-device version. `pnpm version:write` regenerates `native/Cargo.toml` and its `Cargo.lock` entry, and CI fails on drift
- Build tools are pinned: Node in `.node-version`, pnpm in `packageManager` and Rust in `rust-toolchain.toml`, all recorded in `build-inputs.json`, and Inno Setup in `build-inputs.json` alone, with the SHA-256 of its installer: CI installs it into a new folder with `node scripts/inno-setup.mjs --install`, which refuses any other installer, and compiles the Windows installer with the `ISCC.exe` found there. The napi crates are pinned with `=` and the napi CLI exactly; napi and napi-derive move together, since the code napi-derive generates calls into napi: Dependabot brings patch and minor updates of napi, napi-derive and napi-build in one pull request (the `napi` group in `.github/dependabot.yml`), and the addon's build and tests in CI check the versions in it together. No step resolves a floating `latest`
- The addon and the JavaScript are two halves of one build. The addon reports its bridge revision and the urx-device version and commit it was built from; the CLI refuses device access unless they match its own (`src/bridge.ts`, `dist/build-info.js`), and a side that cannot name its commit or version does not match. Both sides change the bridge revision together (`native/src/lib.rs`, `src/bridge.ts`) whenever an export, a method or a record shape of the addon changes
- `pnpm build:release` builds both halves from the recorded commits, never from the working tree. It exports HEAD, with `vendor/urx-device` at the commit the gitlink pins, into a temporary worktree, builds there with `--release` and copies the result, with the launcher at `dist-release/launcher/`, on macOS the removal tool at `dist-release/maintenance/urx-uninstall`, and a record of its files with their SHA-256 and sizes in `dist-release/release-files.json`, into `dist-release/`. Neither build removes or replaces a previous output: each stops before building when anything is at its output, an empty folder or a link included, and publishes with `tools/output`, complete with its record (`release-files.json`, `release-manifest.json`) in a work folder beside the output, then renamed to the output only where nothing is. The output's path shows nothing or the whole output; a build that fails leaves its files in that `<output>.work-…` folder, without the record, and you remove it, as you remove a previous output before building again. A build whose own scratch or export cannot be removed afterwards warns and keeps its result. With `--release`, `scripts/build-info.mjs` and `scripts/build-native.mjs` refuse a checkout whose `vendor/urx-device` is not at the pinned gitlink, whose CLI or urx-device has staged or unstaged changes to tracked files, or whose versions are unknown. A development build embeds whatever it was built from
- `pnpm build:bundle --node-archive <path>` assembles the installed bundle in `dist-bundle/` from a copy of `dist-release/`, taking only the files its record names and refusing one that is missing or changed, a record whose paths are not each one regular file inside the output or that names one file twice, a record that does not name exactly the modules the release's commits compile to, and one without the output's `package.json` saying its modules are ES modules or the common package's `package.json` as its commit holds it, and from the official Node archive, which it reads once and refuses unless its SHA-256 is the one `build-inputs.json` records for this platform; it downloads nothing and refuses a copy taken while `dist-release/` was replaced. The layout is `bin/urx[.exe]` (the launcher), `runtime/node[.exe]`, `app/` (the compiled CLI and the real common package), `native/urx-native.node`, on macOS `maintenance/urx-uninstall`, `notices/` and `release-manifest.json`, which lists every other file with its SHA-256 and size and names the CLI, urx-device and Node it was built from. On macOS its directories and its executables (the launcher, the runtime and the removal tool) are mode 0755 and its other files 0644. In a bundle the addon is looked for in `native/` beside `app/`, elsewhere beside the compiled `native/addon.js`. The notices of the CLI and urx-device are read from the commits the release output names, not from the working tree. `node scripts/check-bundle.mjs dist-bundle` checks a bundle against its manifest and its modes, and runs a copy of it away from the checkout, requiring exactly the modules its commits compile to and loading each of them

## Repository checks

- The `main` ruleset requires the contexts listed in `.github/required-checks.json`. A workflow change keeps every pull-request workflow triggering unfiltered, keeps each gate an `if: always()` job that reads `needs.*.result`, and updates that file and the ruleset together
- Every job, and every step that fetches from outside GitHub, carries a `timeout-minutes`; third-party actions are pinned to a 40-character SHA with a version comment; nothing in CI writes to a pull request's branch
- A Dependabot pull request in which every updated dependency is a patch or a minor update, a minor update of a cargo crate below 1.0 excepted, merges on its own once the required checks pass, the napi group included; a major update, and any pull request that is not one verified Dependabot commit at the head, stays open for a person. `.github/workflows/dependabot-auto-merge.yml` decides it in the job that reports `auto-merge`, a required context, and its header says why each condition is there; `pnpm test dependabot-auto-merge` runs that decision against each kind of update. The merge is attributed to `GITHUB_TOKEN`, so `ci.yml` does not run on its merge commit, and the branch it leaves behind is deleted by hand
